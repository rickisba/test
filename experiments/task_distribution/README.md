# L3GSA 子图(a)：实测速率标定的排队仿真

本版落实用户最新要求：以英文 `GSA (9).pdf` 的硬件与链路配置为准；每请求输入400 tokens、输出1 token；2823、581为设备日志中的prefill tokens/s。中文底稿的历史硬件不用于本版。

**结果是仿真，不是新增硬件测试。** 已验证实现、数值守恒和复现性；目前没有逐请求实测日志，尚不能量化与真实分配结果或时延的误差。增加队列提高了模型的因果完整性，不构成“已证明误差更小”。

## 1. 最容易使用的两个文件

- `simulate_allocation.py`：仿真脚本，顶部 `Settings/CONFIG` 包含所有主配置。
- `plot_allocation.py`：独立绘图脚本，顶部 `STYLE` 包含全部绘图参数。**不需要额外的绘图JSON，也不导入仿真脚本。**

```bash
python -m pip install -r requirements.txt
python simulate_allocation.py --sensitivity
python validate_model.py
python plot_allocation.py
```

只改图片：修改 `plot_allocation.py` 的 `STYLE` 后执行：

```bash
python plot_allocation.py --data output/plot_data.csv --out figures
```

## 3. 物理服务与排队

每台工作站是一个独立、工作守恒的有效token处理服务台，维护FIFO等待队列和运行中的剩余输入工作量。主结果的等效服务需求是400 input tokens，处理速率分别为2823/581 tokens/s。由此推导的400/T是**有效工作量时间**，不是已经实测的单请求TTFT。

请求有以下生命周期：客户端到达 → 链路传输与序列化 → 站点网关选择工作站 → 排队 → 处理输入工作量 → prefill完成 → 响应序列化。记录每个阶段的时刻。请求在队列中超过10秒仍然存在，不会因为路由统计窗口滑过而消失。结束输入后继续排空队列；主图用统计期到达的全部请求作为固定队列成员，避免剔除未在窗口内完成的请求。

一条请求输出1 token的负载定义保留，但没有将未知的首token采样、CPU/API、decode成本硬加进去。导出的 `prefill_surrogate_latency_s` 是模型分量，**不得当作真实TTFT或端到端时延**。

该服务台不复现vLLM continuous batching、KV cache、抢占、张量并行调度或batch效率曲线。`max_batch_requests`只支持对已排队请求进行加和工作量归组，不代表真实GPU batch size，也不能用于证明真实batch调度不影响结果。

没有人为超时、丢弃、有限队列或失败率：队列无限，所有输入最终处理完。排空成功是仿真的守恒条件，不能写成真实100%完成率。

## 4. 路由指标与公平性

两种动态策略共用如下投影归一化工作量指标：

`m_i = (最近一次报告的近W秒已处理输入工作量 + 报告时刻全部未处理输入工作量 + 报告采样后网关已分配的输入工作量 + 当前请求400 tokens)/(报告的站点聚合prefill tokens/s × W)`

W=10 s。已处理工作量包括部分执行进度；未处理工作量包括运行剩余、等待、传输中的已提交输入。网关精确计入自己在报告采样后的分配量，但不偷看未收到的资源报告。指标在两个动态方案中完全一致。

由工作量守恒，`近W秒已处理量 + 当前剩余量 = 近W秒新提交量 + W秒前遗留量`。因此它与原近期分配计数有直接联系，同时保留跨窗口积压。无需额外设定“排队惩罚系数”。资源报告采样/传递使实际决策只使用当时可获知的信息。

| 主图策略 | 实现 |
|---|---|
| L3GSA | 精确请求只到指定模型池；模糊请求比较共同指标 |
| Dyncast-task | 两模型合并为任务级SID，忽略原始模型指定，按同一指标分配。这是特定聚合配置，不是Dyncast全部能力 |
| CoAP-static | 精确请求到指定模型；模糊请求按名义容量权重2823:581固定随机分配。这是特定客户端策略，不是CoAP协议限制 |

同一运行、同一条件中三方案共享到达时刻、任务类别、客户端、静态随机数和服务速率。不同条件共享到达时刻与类别随机排序。任务类别在预热期、统计期分别按目标计数取整后打乱，不宣称每类到达过程都是独立Poisson。

### 固定权重基线的过载

site 2名义份额 `w2=581/3404≈0.17068`。若site 2精确请求比例为p，则CoAP-static的期望site 2到达率为：

`lambda_2 = 24 × [p + (0.9-p) × w2]`。

当p=0.15和0.20时，这个值高于5.81 rps。相应队列不具备稳态；有限时长的等待时间随运行时长增长，不能用来宣称通用稳态延迟收益。主图仍然只是分配组成，不能把排空后的队列成员比例改称窗口内完成goodput。

另附 `auxiliary_control_runs.csv` 的 `Static-demand-aware` 诊断参照，保持主图三曲线不变。该参照**预先知道名义输入类别比例**，按以下固定概率分配模糊请求：

`q2 = clip((w2-p)/(0.9-p), 0, 1)`。

它用于检验固定权重配置的影响，不作为CoAP原生能力，也不声称与在线算法具有完全相同的先验信息。如果该控制达到相近结果，应如实报告，而不能将其隐藏为“无效结果”。

## 5. 图的统计定义

纵轴 = 指定site 2模型且分配至site 2的统计期请求数 / 分配至site 2的全部统计期请求数 ×100%。错误进入site 2的site 1精确请求只计入分母。与旧版本保持同一纵轴语义。

折线是3个独立运行比例的算术均值，误差棒是这3个值的min–max，既不是95%CI也不是标准差。敏感性条件不并入主结果重复次数。

浅蓝参考柱 = `100×min(p/w2,1)`，是名义容量均衡下的流体组成参考，不是一般上界。离散运行值可以略高于它，不能为保持“低于理想值”而改数。

绘图保持3.55×3.05英寸、600 dpi、四点等距、指定坐标标题、浅蓝无边框柱、1.6 pt折线、实心点、左上角黑框图例。等距横轴是分类位置，线段斜率不能当作连续rps导数。

## 7. 后续接入实测数据

`templates/measured_arrivals.csv`：`arrival_s,client_id,kind`。kind=0/1/2对应模糊/site 1精确/site 2精确。若不提供kind，仅回放时刻与客户端，再按场景生成类别；不能将其当作完整实测业务复现。

`templates/measured_rates.csv`：`time_s,site,worker,prefill_tps`。site=1/2，worker=1..4。每条记录表示该工作站的有效服务能力从该时刻变更为该值；采用分段常数，不加合成噪声。不要将需求不足造成的吞吐为零直接填成服务能力为零。

```bash
python simulate_allocation.py --arrivals measured_arrivals.csv --fraction 0.15 --rates measured_rates.csv --out replay
```

回放单条实测到达轨迹时只运行1组，不把同一轨迹重复复制为3次独立实验。速率轨迹需要覆盖实际建模时段；轨迹起始前使用标称值，最后一条之后保持最后值，必须在论文中说明这种边界处理。

`compare_measurements.py`可比较同一业务条件下的独立实测site 2分配计数，输出比例的MAE/RMSE/偏差（百分点）。模板只有字段，无伪造测量数据：

```bash
python compare_measurements.py --measured real_allocation_counts.csv
```

要缩小实际误差，下一步应校验每工作站的稳定饱和prefill吞吐及四副本聚合能力，回放实际到达与类别序列，再用**未用于标定**的运行验证分配组成。真实时延还需要队列、batch和首token时间日志。当前不能给出任何实测误差百分比。

## 8. 方法核对来源

- vLLM v0.11.0 `get_throughput`：按日志间隔的token计数计算吞吐，提示“日志实测速率”不自动等于饱和容量。https://docs.vllm.ai/en/v0.11.0/api/vllm/engine/metrics.html

这些来源不规定本次Gamma形状、报告周期、网络payload或服务批次大小；以上数值均按各自来源单独说明。

## 10. 设备吞吐波动与指标分母

新增可选的设备级吞吐波动敏感性检查，恒定吞吐主图保留为参照：

```bash
python simulate_allocation.py --sensitivity --capacity-variation
```

四个附加场景比较单设备CV为5%/10%的独立波动，以及10%波动中站点内50%/100%共同对数方差。
采样间隔1 s、相关时间5 s均为模型假设，CV不是最大涨跌幅。过程改变实际处理速率和服务完成时刻，
不对图线加噪声或强制降低末点。每个场景仍是独立的3次运行，不能合并成15次重复。

主图 `precise_at_site2_pct` 的分母是**分配到site 2的全部任务**。
新增 `site2_precise_sent_to_site2_pct` 的分母是**输入中所有要求site 2模型的精确任务**；它记录分配目的地，
不是包送达或业务成功率。另列窗口结束前的模型prefill完成比例，避免将分配和完成混淆。
空分母输出为空，不伪造0%或100%。

详细公式、四台设备聚合的影响及结果见 [CAPACITY_VARIATION.md](CAPACITY_VARIATION.md)。
每个场景的配置和观察到的设备/池均值与CV均保留；原始每秒速率轨迹可以从种子重新生成。
